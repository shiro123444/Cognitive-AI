# EduFish Document Editorial Redesign Design

> Date: 2026-05-08
> Scope: `docs/edufish` design/development document body redesign
> Status: approved design draft

---

## 1. Goal

`docs/edufish/edufish设计与开发文档.pdf` 的封面已经建立了合适的气质：克制、安静、正式、带一点提案感。

问题集中在封面之后的正文系统：

1. 页型过于单一，几乎所有内页都在重复“标题 + 正文 / 表格 / 图”的同一模板。
2. 章节起始页留白很多，但留白没有承担结构作用，页面显得空而不是从容。
3. 中段表格页密度高、信息同权，读起来像导出表，不像被编辑过的 proposal。
4. flowchart、chart、code block 更像技术占位内容，缺少图示语言和叙事价值。

本次设计目标不是重写文案，也不是改成高饱和彩色画册，而是：

1. 保留现有封面主气质。
2. 将正文从“技术说明书排版”提升为“编辑化科技提案书排版”。
3. 建立一套稳定的正文页型系统、留白规则、图示语言和弱色彩系统。
4. 让评审者在更短时间内抓到结论、层级和重点。

---

## 2. Context Findings

### 2.1 Existing Assets

当前文档核心输入与渲染资产：

1. 内容源：`docs/edufish/edufish-design-development-content.json`
2. 正文渲染器：`docs/edufish/.pdf-build/render_body-left.py`
3. 封面模板：`docs/edufish/.pdf-build/cover.html`
4. 设计 tokens：`docs/edufish/.pdf-build/tokens.json`

现有实现已具备以下基础：

1. A4 内页渲染框架稳定。
2. 封面风格已经可用。
3. 表格、代码、chart、flowchart 都有独立 block 类型。
4. 可以通过修改 renderer 和 tokens 完成系统级升级，而不是逐页手工修 PDF。

### 2.2 Current Rendering Issues

结合当前 PDF 预览，主要问题如下：

1. 章节页如“二、引擎架构与接入模型”“四、多智能体协同分析”“七、干预策略推演”都只有大标题和短正文，页面纵向张力不足。
2. 表格页如接入方式、功能模块、运行环境大量依赖满宽表格，行列层级弱。
3. flowchart 基本是垂直串联框，清楚但不精细，缺少模块关系、注释和视觉节奏。
4. code 页视觉权重过高，像开发输出，不像评审证据。
5. chart 已经比 flowchart 好一些，但仍然是“图在上，caption 在下”的单向排法，缺少判断先行。

### 2.3 Product / Repo Alignment

最近提交历史表明，EDUFISH 本身正在朝更完整的引擎、知识图谱和企业级特性方向推进，而不是做营销化展示。因此文档应体现：

1. 可信、克制、结构化。
2. 能承载技术细节，但不让细节淹没结论。
3. 有设计感，但不削弱评审文档的正式度。

## 3. Approaches Considered

### 3.1 Approach A: Academic Proposal Lite

特点：

1. 黑白灰为主。
2. 轻微修正文档节奏。
3. 基本保留现有表格和图示结构。

优点：

1. 风险最低。
2. 最接近传统正式文档。

缺点：

1. 后半部分仍然容易落回“高级 Word”。
2. 很难显著改善图示精细度和页间节奏。

### 3.2 Approach B: Editorial Tech Proposal

特点：

1. 保留封面克制与学术感。
2. 正文使用编辑化版式。
3. 引入非常轻的冷色强调。
4. flowchart / table / code block 全部升级为提案书式表达。

优点：

1. 设计感明显提升。
2. 保持正式、可信。
3. 最适合现有内容密度和评审场景。

缺点：

1. 需要改 renderer，而不只是改 tokens。
2. 需要建立页型系统和新图示语言。

### 3.3 Approach C: Portfolio / Showcase Deck

特点：

1. 页面更像作品集或 pitch deck。
2. 视觉表达更强。
3. 图表和模块卡片化更重。

优点：

1. 视觉冲击强。

缺点：

1. 易削弱正式度。
2. 可能与当前封面和评审语境脱节。

### 3.4 Recommendation

采用 **Approach B: Editorial Tech Proposal**。

原因：

1. 它承接现有封面最自然。
2. 它允许在不改变文档核心内容的前提下明显提升精致度。
3. 它能把图示、表格、代码和留白一起纳入同一套系统，而不是分散修补。

## 4. Design Direction

### 4.1 Visual Tone

整体语气定义为：

1. 冷静
2. 轻科技
3. 编辑化
4. 提案书感

明确避免：

1. 高饱和赛博视觉
2. 大面积彩色背景
3. 过于学术模板化的论文排版
4. 像宣传册一样弱化技术可信度

### 4.2 Color System

主体色仍为：

1. 黑
2. 白
3. 不同层级的灰

新增一组极轻冷色强调，优先方向：

1. 雾蓝
2. 冷灰蓝
3. 青灰

强调色只允许用于：

1. 章节导视
2. 小标签
3. 图示节点 / 连线强调
4. 重点数据或关键行标记

不允许用于：

1. 大面积页面铺底
2. 整表高亮
3. 影响正文可读性的装饰性渐变

### 4.3 Typography

保留现有封面的显示字体气质，正文维持简洁的人文无衬线阅读感。

内页升级重点：

1. 标题与正文之间拉开更明确层级。
2. 正文阅读列略收窄，减少“整块铺陈”。
3. 引导句、判断句、caption、小标签各有独立层级。

---

## 5. Page-Type System

本次 redesign 不再让所有内页复用同一正文模板，而是建立 5 类固定页型。

### 5.1 Section Opening Page

适用于每章起始页。

结构：

1. 超大章节编号与标题
2. 一句章节主张
3. 2-3 个关键词标签
4. 一条轻导视线或轻信息块
5. 精心控制的仪式性留白

目标：

1. 让章节页承担“导语”功能，而不是只做分页。
2. 让空白有结构，不是简单留空。

### 5.2 Editorial Narrative Page

适用于摘要、问题定义、设计原则、人性化设计要求等正文说明页。

结构：

1. 收窄的主阅读列
2. 更明确的段间呼吸
3. 关键判断句抽离成引导句或侧向短句
4. callout 与正文不再视觉同权

目标：

1. 提升阅读速度。
2. 避免所有内容都是一整块正文。

### 5.3 Diagram Explanation Page

适用于架构图、流程图、部署图。

结构：

1. 图示作为主视觉
2. 图旁或图前先给一句判断
3. 图注不再只是机械 caption，而是与图一起说明“这张图证明什么”

目标：

1. 图示承担解释责任。
2. 页面看起来像 proposal diagram，而不是开发草图截图。

### 5.4 Comparison Table Page

适用于接入方式、功能模块、路线图、运行环境等表格密集页面。

结构：

1. 先给结论或判断句
2. 主表承载系统信息
3. 重点行 / 重点列做局部强调
4. 控制横线、底纹和行高，避免整页同权

目标：

1. 让表格先传达主结论，再支持细读。

### 5.5 Technical Evidence Page

适用于 JSON、API、配置、命令行片段。

结构：

1. 上方一句解释“这段代码 / 配置证明了什么”
2. 代码块做成轻量技术证据块
3. 代码视觉宽度与高度受控
4. 必要时优先展示关键片段而不是整块原文

目标：

1. 让技术细节服务于论点，而不是接管页面。

## 6. Layout and Whitespace Rules

### 6.1 Two Kinds of Whitespace

本次 redesign 将留白拆为两类：

1. `仪式性留白`
   用在章节开场页、重要图示页，让页面有气口和停顿。
2. `功能性留白`
   用在正文段落、表格、图示、caption 与结论句之间，帮助分层和阅读。

### 6.2 Chapter Opening Rhythm

当前章节页的空白没有被组织，因此显空。

改版后章节起始页应满足：

1. 标题上方、下方留白不对称，形成方向感。
2. 不再只依赖一根横线做分隔。
3. 页面上至少有两个视觉锚点，而不是只剩标题。

### 6.3 Reading Column Width

正文页应收窄主阅读列，避免 A4 宽页面上长段文字横向过长。

收益：

1. 行长更舒服。
2. 页面更像被编辑过。
3. 与图表、callout 的并置更自然。

### 6.4 Page Density Strategy

根据页型区别对待密度：

1. 章节页允许轻密度。
2. 正文页保持中密度。
3. 表格页和证据页保持高信息量，但主次必须清晰。

---

## 7. Table Design

### 7.1 Problems to Solve

现有表格主要问题：

1. 每行每列视觉权重接近。
2. 满宽使用过多。
3. 线条和底纹只是分隔，没有表达主次。
4. 长表读起来像数据库导出。

### 7.2 New Table Hierarchy

表格统一采用三层信息层级：

1. `主信息`
   更稳字重、更清晰行高、较高对比度。
2. `次信息`
   更浅灰度、较轻节奏。
3. `重点项`
   用极轻强调色、局部标尺、边线或标签突出。

### 7.3 Table Styling Rules

规则：

1. 降低无意义横线数量。
2. 减少满页“黑头 + 灰白棋盘格”的机械感。
3. 适度增加关键行的上下 padding。
4. 对长文本列做更优换行和列宽控制。
5. 对最重要的 1-2 行或 1 列提供局部强调。

### 7.4 Candidate Pages

优先优化以下表格页：

1. 接入方式
2. 引擎核心能力模块
3. 实施路线图
4. 运行环境
5. 生产部署建议
6. 风险与治理

---

## 8. Diagram Language

### 8.1 Problems to Solve

现有 flowchart 清楚但不精细，主要问题：

1. 以垂直串联框为主，页面张力弱。
2. 架构图、流程图、部署图采用同一种语法，无法区分表达意图。
3. 节点与连接只承担“连接”作用，缺少层级和注释。

### 8.2 Target Style

采用“提案书式轻视觉信息图”，特点：

1. 节点造型更克制，不花哨。
2. 层级、关系、重点比外轮廓更重要。
3. 注释短、小、贴近结构。
4. 图本身应能传达一条清晰判断。

### 8.3 Diagram Families

#### Architecture Diagram

用于引擎分层、系统模块关系。

要求：

1. 强调层级和模块边界。
2. 节点之间有节奏变化，不是等距离串珠。
3. 通过轻色高亮核心闭环或关键中枢。

#### Process Diagram

用于接入、分析、推演、实施路径。

要求：

1. 强调路径与状态变化。
2. 返回路径、人工复核路径与主流程区分。
3. 关键步骤可带轻注释。

#### Deployment Diagram

用于运行环境与依赖关系。

要求：

1. 强调组件关系与外部依赖。
2. 少做流程感，多做拓扑感。
3. 清楚区分宿主平台、引擎、存储、模型服务。

### 8.4 Caption Strategy

caption 不再只是“Figure N: 说明”。

新规则：

1. 重要图页前置一句判断。
2. caption 负责补充，而不是承担全部说明。
3. 图和说明应形成一个整体版面。

---

## 9. Code and Chart Treatment

### 9.1 Code Blocks

代码块定位从“主要内容”改为“技术证据”。

规则：

1. 视觉上更轻、更窄、更克制。
2. 上方必须有一句说明其意义。
3. 默认优先展示关键片段。
4. 保留可读性，但减少开发控制台感。

### 9.2 Charts

chart 已有基础，但需要更 proposal 化。

规则：

1. 图表页先给结论句，再放图。
2. 使用更克制的坐标线和标签层级。
3. 重点数据允许有轻强调色。
4. 避免“标题 + 图 + caption”三段式机械堆叠。

## 10. Implementation Design

### 10.1 Files in Scope

本次实现主要涉及：

1. `docs/edufish/.pdf-build/render_body-left.py`
2. `docs/edufish/.pdf-build/tokens.json`
3. `docs/edufish/edufish-design-development-content.json`
4. 必要时补充 `docs/edufish/.pdf-build` 内的辅助预览或生成资产

### 10.2 Rendering Changes

实现上不建议逐页手工改，而应在 renderer 上增加能力：

1. 支持章节开场页样式。
2. 支持“判断句 / 标签 / 侧向说明”类 block。
3. 升级 table block 的层级和重点行表现。
4. 升级 flowchart block 的视觉语法，按架构 / 流程 / 部署分类渲染。
5. 升级 code block 为技术证据块。
6. 优化 chart block 的结论先行版式。

### 10.3 Content Adjustments

内容文件只做结构性调整，不重写整份文案。

允许的内容改动：

1. 为章节起始页补充一句判断语。
2. 为关键图表补充结论句。
3. 将部分长 code block 裁切成关键片段。
4. 为表格增加重点标记元数据。

不做的内容改动：

1. 大规模改文案。
2. 改技术结论。
3. 改章节结构。

## 11. Error Handling and Constraints

### 11.1 Constraints

必须满足：

1. 封面主视觉不重做。
2. 整体仍适合 A4 PDF 输出。
3. 中文可读性优先于形式实验。
4. 新样式不能让内容溢出或造成分页失控。

### 11.2 Risks

主要风险：

1. 图示改得太“设计化”会削弱正式感。
2. 表格强调过度会影响整体克制气质。
3. 章节页如果增加过多元素，会与封面断裂。
4. renderer 级改动可能引入分页回归。

### 11.3 Mitigations

应对策略：

1. 所有强调色控制在极轻范围。
2. 优先提高结构清晰度，不追求视觉炫技。
3. 先统一页型系统，再做局部增强。
4. 每轮改动都用 preview 图和完整 PDF 检查分页。

---

## 12. Verification Plan

实现完成后至少验证以下内容：

1. 章节起始页不再出现“只有标题和大空白”的弱页面。
2. 主要表格页的重点能在 3 秒内被定位。
3. flowchart 能明显区分架构图、流程图、部署图三类语法。
4. code 页不再成为主视觉负担。
5. PDF 全文分页稳定，没有内容溢出、截断、重叠。
6. 封面与正文之间衔接自然，没有视觉断层。

---

## 13. Scope Decision

本次执行范围确定为：

1. 重做正文页型系统。
2. 重做章节开场页。
3. 重做所有 flowchart 的图示语言。
4. 优化主要表格页的密度与重点层级。
5. 优化代码页和图表页的视觉权重。
6. 保留封面，只做极小衔接调整。

明确不在本次范围内：

1. 重写整份文案。
2. 改成展示型画册或营销型 deck。
3. 引入大面积彩色背景。
4. 变更文档的技术主张和章节结构。

---

## 14. Final Recommendation

执行版本定为：

1. 风格：`编辑化科技提案型`
2. 图示：`提案书式轻视觉信息图`
3. 色彩：`黑白灰骨架 + 极轻冷色强调`
4. 结果目标：保留封面气质，将正文从说明书提升为精致 proposal

这是当前内容密度、评审语境和现有封面之间最协调的方案。
